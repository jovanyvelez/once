🧠 1. Conceptos fundamentales

1.1 ¿Qué es el I/O?

I/O significa Input / Output (entrada / salida). Cada vez que tu programa habla con algo externo —disco, red, base de datos— hay espera. Y esperar es caro.

☕ Analogía: La cafetería Síncrono (bloqueante): Pedís un café. Te quedás parado en la caja esperando a que esté listo. No hacés nada más. Toda la fila espera detrás tuyo.

Asíncrono (no bloqueante): Pedís el café, te dan un numerito. Te sentás, revisás el celu, hablás con un amigo. Cuando tu café está listo, te avisan. Mientras tanto, el cajero atendió a 10 personas más.

1.2 Tabla comparativa: Dos modelos de ejecución

Característica Síncrono (def + requests / psycopg2) Asíncrono (async def + httpx / asyncpg)
Bloquea otras tareas ✅ Sí. Una petición bloquea a las demás. ❌ No. Mientras espera I/O, atiende otras peticiones.
Concurrencia Requiere múltiples hilos/procesos (más RAM, más complejidad) Miles de conexiones concurrentes en un solo hilo.
Uso de CPU Usa todos los cores (multithreading real) Un solo core por proceso. Se escala con réplicas.
Ideal para Tareas CPU-intensivas (cálculos, IA, renders) Tareas I/O-intensivas (APIs, BBDD, microservicios)
Curva de aprendizaje Más simple y predecible Requiere entender async/await y event loop
Regla de oro: Nunca mezcles código bloqueante dentro de una función async def. Si lo hacés, congelás todo el event loop. Usá librerías asíncronas (asyncpg en vez de psycopg2, httpx en vez de requests, etc.).

1.3 El Event Loop (bucle de eventos)

Es el "director de orquesta" del asyncio. Imaginalo como un repartidor con muchas entregas. Mientras espera que un destinatario abra la puerta, no se queda parado: va a otro domicilio, entrega otro paquete, y vuelve.

🔄 2. Lifespan — El ciclo de vida de tu aplicación

2.1 ¿Qué problema resuelve?

Tu backend necesita recursos que viven toda la ejecución: conexiones a base de datos, clientes HTTP, modelos de ML, caches. Sin embargo, no querés crearlos cada vez que llega una petición. Querés crearlos una sola vez cuando la app arranca y destruirlos cuando se apaga.

🏗️ Analogía: La inauguración de un edificio Lifespan = startup + shutdown
Antes de abrir las puertas (startup), conectás la electricidad, el agua y preparás las oficinas. Una vez listo, abrís y atendés gente todo el día. Al cerrar (shutdown), apagás todo ordenadamente. No instalás la electricidad cada vez que entra un cliente.

2.2 El decorador @asynccontextmanager

Python provee contextlib.asynccontextmanager para crear funciones que tienen un "antes" (todo lo que va antes del yield) y un "después" (todo lo que va después del yield).

from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ===== STARTUP: se ejecuta UNA SOLA VEZ al iniciar =====
    print("🔥 Iniciando...")
    app.state.db = await asyncpg.create_pool(dsn)
    
    yield  # ← La app está viva y sirviendo peticiones
    
    # ===== SHUTDOWN: se ejecuta UNA SOLA VEZ al apagar =====
    print("🛑 Apagando...")
    await app.state.db.close()

2.3 Línea de tiempo del lifespan

2.4 ¿Dónde guardar cosas globales? app.state

FastAPI ofrece app.state, un objeto tipo bolsa donde podés guardar cualquier cosa que necesite toda la aplicación:

# En el lifespan:
app.state.pool = await asyncpg.create_pool(...)
app.state.config = cargar_configuracion()
app.state.modelo_ml = cargar_modelo()

# En cualquier ruta o dependencia:
async def get_db():
    async with request.app.state.pool.acquire() as conn:
        yield conn

Importante: Si tu app tiene múltiples workers (gunicorn con varios procesos), cada worker ejecuta su propio lifespan. No compartas estado entre procesos sin usar Redis, BD o similar.

💉 3. Depends — Inyección de dependencias

3.1 ¿Qué significa "inyectar dependencias"?

Es un patrón donde no creás los objetos que necesitás dentro de tu función; en cambio, se los pedís al framework y él te los entrega listos. Esto hace que tu código sea más testeable y menos acoplado.

🔌 Analogía: El cargador universal En vez de que cada dispositivo tenga su propia batería soldada, usás un cargador externo. El dispositivo depende del cargador (lo necesita), pero no sabe fabricarlo. Depends es el enchufe de la pared: vos pedís "necesito una conexión a BD" y FastAPI te la enchufa.

3.2 Sintaxis básica

from fastapi import Depends

# 1. Definís una función que retorna lo que necesitás
async def obtener_conexion() -> Connection:
    async with pool.acquire() as conn:
        yield conn

# 2. La ruta "declara" su dependencia en los parámetros
@app.get("/usuarios")
async def listar_usuarios(
    conn: Connection = Depends(obtener_conexion)  # ← ¡inyección!
):
    return await conn.fetch("SELECT * FROM usuarios")

3.3 ¿Qué pasa por debajo?

  1. Llega un GET a /usuarios FastAPI ve que la ruta tiene parámetros con Depends(...).
  2. FastAPI llama a cada dependencia Antes de ejecutar tu ruta, resuelve todas las dependencias en orden. Si una dependencia depende de otra, la resuelve recursivamente.
  3. FastAPI pasa los resultados Una vez resueltas, ejecuta tu función listar_usuarios con los valores reales.
  4. Si la dependencia usa yield La parte después del yield se ejecuta cuando la respuesta ya fue enviada (para cerrar recursos).

3.4 Dependencias que dependen de dependencias (¡encadenamiento!)

Esta es la magia real: podés componer dependencias como bloques de LEGO.

async def get_db() -> Connection:
    async with pool.acquire() as conn:
        yield conn

class UsuarioService:
    def __init__(self, conn):
        self.conn = conn
    async def crear(self, nombre: str):
        return await self.conn.fetchrow(...)

# Esta dependencia "encadena" con la anterior
async def get_servicio(conn = Depends(get_db)):
    return UsuarioService(conn)

# La ruta solo pide el servicio, no la conexión
@app.post("/usuarios")
async def crear_usuario(
    nombre: str,
    servicio: UsuarioService = Depends(get_servicio)
):
    return await servicio.crear(nombre)
FastAPI cachea dependencias dentro de una misma petición. Si tres dependencias piden Depends(get_db), la llamada a get_db se ejecuta una sola vez para esa petición. Esto evita abrir 3 conexiones para la misma request.

3.5 Casos de uso típicos de Depends

  • Conexión a BD — Pedir una conexión del pool por request.
  • Autenticación — Verificar JWT, extraer usuario actual.
  • Permisos — Verificar que el usuario tenga rol "admin".
  • Validación de parámetros complejos — Por ej, parsear filtros de query string.
  • Header / Cookie parsing — Extraer y validar headers personalizados.
  • Contexto de request — Request ID, idioma del usuario, timezone.

⚡ 4. asyncpg — El traductor relámpago

4.1 ¿Qué es asyncpg exactamente?

Es una librería de Python que implementa el protocolo de PostgreSQL de forma nativa (sin envolver libpq en C) y 100% asíncrona. Fue escrita desde cero en Python + Cython para ser la más rápida.

4.2 ¿Por qué es tan rápido?

RazónExplicación
Protocolo binario No convierte datos a texto para enviarlos. Habla directamente el lenguaje binario de PostgreSQL, lo que elimina el costo de serializar/deserializar a strings.
Prepared statements automáticos La primera vez que ejecutás un query, asyncpg lo prepara en el servidor. Las siguientes llamadas reutilizan el plan de ejecución, evitando re-parseo.
Escrito en Cython Las partes críticas (parseo de mensajes del protocolo) están compiladas a C, no interpretadas como Python puro.
Zero-copy I/O Cuando recibe datos del socket, no los copia innecesariamente entre buffers.
Sin GIL en operaciones de red Las operaciones de I/O liberan el GIL, permitiendo verdadero paralelismo con threads si fuera necesario.

4.3 Instalación

pip install asyncpg

4.4 Métodos principales de una conexión

MétodoRetorna¿Cuándo usarlo?
conn.execute(sql, *args) str (ej: "INSERT 0 1") INSERT, UPDATE, DELETE, CREATE TABLE (no esperás filas de vuelta, solo confirmación)
conn.fetch(sql, *args) list[Record] SELECT que devuelve múltiples filas
conn.fetchrow(sql, *args) Record | None SELECT que devuelve una sola fila (o ninguna)
conn.fetchval(sql, *args) Any | None SELECT que devuelve un solo valor escalar (COUNT, MAX, etc.)
conn.executemany(sql, items) None Insertar muchos registros a la vez (bulk insert)
conn.copy_to_table(...) None Carga masiva ultra-rápida vía protocolo COPY

4.5 Ejemplos de cada método

# ── execute: no retorna filas ──
status = await conn.execute(
    "INSERT INTO alumnos(nombre, nota) VALUES($1, $2)",
    "María", 9.5
)
print(status)  # "INSERT 0 1"

# ── fetch: retorna lista de filas ──
filas = await conn.fetch("SELECT id, nombre FROM alumnos WHERE nota > $1", 7)
for fila in filas:
    print(fila['nombre'], fila['nota'])  # Se accede como dict

# ── fetchrow: retorna una fila o None ──
fila = await conn.fetchrow("SELECT * FROM alumnos WHERE id = $1", 5)
if fila:
    print(dict(fila))  # Convertir a dict para JSON

# ── fetchval: retorna un valor escalar ──
total = await conn.fetchval("SELECT COUNT(*) FROM alumnos")
print(f"Hay {total} alumnos")

# ── executemany: bulk insert ──
datos = [("Ana", 8.0), ("Luis", 6.5), ("Sofía", 9.8)]
await conn.executemany(
    "INSERT INTO alumnos(nombre, nota) VALUES($1, $2)",
    datos
)

4.6 Placeholders: $1, $2, $3...

asyncpg usa placeholders numéricos con signo $, muy distinto a otras librerías. Esto es adrede y más seguro.

LibreríaSintaxisEjemplo
asyncpg$1, $2WHERE id = $1
psycopg2%sWHERE id = %s
sqlite3?WHERE id = ?
SQLAlchemy:nombreWHERE id = :id
NUNCA hagas esto: f"SELECT * FROM users WHERE name = '{nombre}'"

Esto se llama SQL Injection y es la vulnerabilidad #1 en aplicaciones web. Si nombre contiene '; DROP TABLE users; --, perdiste toda la base de datos. Usá siempre placeholders.

🏊 5. Pool de conexiones

5.1 El problema de las conexiones

Abrir una conexión a PostgreSQL no es barato: involucra TCP handshake, autenticación SSL, negociación de parámetros... puede tomar 20-50ms. Si tu API recibe 1000 peticiones por segundo y cada una abre una conexión nueva, tu base de datos colapsa.

5.2 ¿Cómo funciona un pool?

Un pool mantiene un número fijo de conexiones ya abiertas y listas para usar. Cuando tu ruta necesita una, la toma prestada del pool. Cuando termina, la devuelve. Como alquilar un auto por minuto en vez de fabricar uno cada vez.

5.3 Crear y configurar el pool

import asyncpg

pool = await asyncpg.create_pool(
    dsn="postgresql://user:password@localhost:5432/basedatos",
    min_size=2,      # Mínimo de conexiones siempre vivas
    max_size=10,     # Máximo de conexiones simultáneas
    max_queries=50000, # Cerrar conexión tras N queries (evita memory leaks)
    max_inactive_connection_lifetime=300, # 5 min inactiva → se cierra
    timeout=30.0,   # Segundos de espera máxima si el pool está lleno
)

5.4 Patrón correcto: tomar y devolver

async def get_db() -> Connection:
    # Toma prestada UNA conexión del pool
    async with pool.acquire() as conn:
        yield conn  
    # Al salir del with, conn se devuelve automáticamente al pool

# La ruta usa la dependencia, y al terminar se libera
@app.get("/datos")
async def obtener_datos(conn = Depends(get_db)):
    return await conn.fetch("SELECT * FROM tabla")
Error común: Tomar una conexión del pool y no devolverla. Si las 10 conexiones están "tomadas" sin devolver, la petición #11 se queda esperando hasta que haya timeout. Para evitar esto, usá SIEMPRE async with pool.acquire() as conn o un yield en Depends.

5.5 Conexiones y límites de PostgreSQL

PostgreSQL tiene un límite de conexiones simultáneas (por defecto 100). Si tenés 5 instancias de tu app, cada una con max_size=25, ya son 125 conexiones: te pasaste del límite. La fórmula segura es:

max_connections_postgres >= (instancias_de_app × max_size_del_pool) + 5 (reserva para pgAdmin, migraciones, etc.)

🛠️ 6. Tu primera API completa con FastAPI + asyncpg

Juntemos todo lo aprendido en un solo archivo funcional. Asumimos que ya existe una tabla alumnos(id SERIAL PRIMARY KEY, nombre TEXT, nota FLOAT).

from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends, HTTPException
import asyncpg

# ═══════════════════════════════════════════════════════════
# LIFESPAN: Inicialización y apagado del pool
# ═══════════════════════════════════════════════════════════
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.pool = await asyncpg.create_pool(
        "postgresql://user:pass@localhost:5432/colegio",
        min_size=2,
        max_size=10
    )
    yield
    await app.state.pool.close()

app = FastAPI(lifespan=lifespan, title="API Colegio")

# ═══════════════════════════════════════════════════════════
# DEPENDENCIA: Obtener conexión del pool
# ═══════════════════════════════════════════════════════════
async def get_db() -> asyncpg.Connection:
    async with app.state.pool.acquire() as conn:
        yield conn

# ═══════════════════════════════════════════════════════════
# RUTAS
# ═══════════════════════════════════════════════════════════

@app.post("/alumnos/", status_code=201)
async def crear_alumno(
    nombre: str,
    nota: float,
    conn = Depends(get_db)
):
    await conn.execute(
        "INSERT INTO alumnos(nombre, nota) VALUES($1, $2)",
        nombre, nota
    )
    return {"mensaje": f"Alumno '{nombre}' creado"}

@app.get("/alumnos/")
async def listar_alumnos(
    nota_minima: float = 0.0,
    conn = Depends(get_db)
):
    filas = await conn.fetch(
        "SELECT id, nombre, nota FROM alumnos WHERE nota >= $1 ORDER BY nota DESC",
        nota_minima
    )
    return [dict(f) for f in filas]

@app.get("/alumnos/{alumno_id}")
async def obtener_alumno(
    alumno_id: int,
    conn = Depends(get_db)
):
    fila = await conn.fetchrow(
        "SELECT id, nombre, nota FROM alumnos WHERE id = $1",
        alumno_id
    )
    if not fila:
        raise HTTPException(status_code=404, detail="Alumno no encontrado")
    return dict(fila)

@app.put("/alumnos/{alumno_id}")
async def actualizar_alumno(
    alumno_id: int,
    nombre: str = None,
    nota: float = None,
    conn = Depends(get_db)
):
    # Construir update dinámico (solo los campos enviados)
    sets = []
    args = []
    idx = 1
    if nombre is not None:
        sets.append(f"nombre = ${idx}")
        args.append(nombre); idx += 1
    if nota is not None:
        sets.append(f"nota = ${idx}")
        args.append(nota); idx += 1

    if not sets:
        raise HTTPException(status_code=400, detail="Nada que actualizar")

    args.append(alumno_id)
    sql = f"UPDATE alumnos SET {', '.join(sets)} WHERE id = ${idx}"
    result = await conn.execute(sql, *args)

    if result == "UPDATE 0":
        raise HTTPException(status_code=404, detail="Alumno no encontrado")
    return {"mensaje": "Alumno actualizado"}

@app.delete("/alumnos/{alumno_id}")
async def eliminar_alumno(
    alumno_id: int,
    conn = Depends(get_db)
):
    result = await conn.execute(
        "DELETE FROM alumnos WHERE id = $1", alumno_id
    )
    if result == "DELETE 0":
        raise HTTPException(status_code=404, detail="Alumno no encontrado")
    return {"mensaje": "Alumno eliminado"}

Explicación línea por línea del concepto más importante: el flujo

  1. El servidor arranca FastAPI ejecuta lifespan(). Se crea el pool con 2 a 10 conexiones listas. El yield le dice a FastAPI "ya podés empezar a recibir peticiones".
  2. Llega un POST /alumnos/?nombre=Juan¬a=8.5 FastAPI parsea los parámetros. Ve el Depends(get_db) y ejecuta get_db(), que toma una conexión libre del pool.
  3. Se ejecuta la ruta conn.execute("INSERT INTO alumnos...", "Juan", 8.5). asyncpg envía el comando en binario, PostgreSQL lo ejecuta, devuelve "INSERT 0 1". La ruta retorna el JSON de respuesta.
  4. La conexión se devuelve al pool Como get_db usaba async with pool.acquire(), al salir del with la conexión vuelve al pool. Está limpia y lista para la próxima petición.

🏗️ 7. Arquitectura de 3 capas (Nivel Pro)

7.1 ¿Por qué separar en capas?

Imaginá un archivo de 5000 líneas con 40 endpoints, validaciones, SQL crudo y reglas de negocio mezclados. Bienvenido al código espagueti: imposible de testear, mantener o entender.

Las 3 capas son el estándar de la industria para mantener el código organizado, testeable y reutilizable:

🏢 Analogía: Una empresa
1. Recepción
(Rutas / Presentación)		 Atiende al cliente, recibe su pedido, le entrega el resultado. No sabe nada de cómo se hace el trabajo.
2. Oficina
(Servicios / Negocio)		 Recibe la orden de recepción, aplica las reglas del negocio, coordina quién hace qué. No sabe nada de HTTP ni bases de datos.
3. Depósito
(Repositorios / Datos)		 Solo sabe buscar, guardar y modificar cosas en la base de datos. No sabe para qué se usan esos datos.

7.2 La estructura de carpetas profesional

mi_api/
├── main.py              ← FastAPI app + lifespan + router principal
├── config.py            ← Variables de entorno, DSN, settings
├── routers/
│   └── alumnos.py       ← Endpoints (solo reciben petición, llaman servicio, devuelven respuesta)
├── services/
│   └── alumnos.py       ← Lógica de negocio (validaciones, reglas, orquestación)
├── repositories/
│   └── alumnos.py       ← Operaciones CRUD contra PostgreSQL (SQL puro)
├── models/
│   └── alumnos.py       ← Schemas Pydantic para request/response
└── requirements.txt

7.3.2 Repositorio (capa de datos)

# repositories/alumnos.py
import asyncpg

class AlumnoRepository:
    def __init__(self, conn: asyncpg.Connection):
        self.conn = conn

    async def crear(self, nombre: str, nota: float) -> int:
        return await self.conn.fetchval(
            "INSERT INTO alumnos(nombre, nota) VALUES($1, $2) RETURNING id",
            nombre, nota
        )

    async def obtener_por_id(self, id: int) -> dict | None:
        fila = await self.conn.fetchrow(
            "SELECT id, nombre, nota FROM alumnos WHERE id = $1", id
        )
        return dict(fila) if fila else None

    async def listar(self, nota_min: float = 0) -> list[dict]:
        filas = await self.conn.fetch(
            "SELECT id, nombre, nota FROM alumnos WHERE nota >= $1 ORDER BY nota DESC",
            nota_min
        )
        return [dict(f) for f in filas]

    async def actualizar(self, id: int, nombre: str | None, nota: float | None) -> bool:
        sets, args, idx = [], [], 1
        if nombre is not None:
            sets.append(f"nombre = ${idx}"); args.append(nombre); idx += 1
        if nota is not None:
            sets.append(f"nota = ${idx}"); args.append(nota); idx += 1
        if not sets: return False
        args.append(id)
        sql = f"UPDATE alumnos SET {', '.join(sets)} WHERE id = ${idx}"
        result = await self.conn.execute(sql, *args)
        return result != "UPDATE 0"

    async def eliminar(self, id: int) -> bool:
        result = await self.conn.execute(
            "DELETE FROM alumnos WHERE id = $1", id
        )
        return result != "DELETE 0"

7.3.3 Servicio (capa de negocio)

# services/alumnos.py
from repositories.alumnos import AlumnoRepository

class AlumnoService:
    def __init__(self, repo: AlumnoRepository):
        self.repo = repo

    async def inscribir(self, nombre: str, nota: float) -> dict:
        # Regla de negocio: validar nota
        if nota < 1 or nota > 10:
            raise ValueError("La nota debe estar entre 1 y 10")
        if not nombre.strip():
            raise ValueError("El nombre no puede estar vacío")

        # Podrías agregar más reglas acá: validar duplicados, notificar, logging, etc.
        id_nuevo = await self.repo.crear(nombre.strip(), nota)
        return {"id": id_nuevo, "nombre": nombre, "nota": nota}

    async def obtener(self, id: int) -> dict:
        alumno = await self.repo.obtener_por_id(id)
        if not alumno:
            raise ValueError("Alumno no encontrado")
        return alumno

    async def listar_aprobados(self, nota_min: float = 6) -> list[dict]:
        return await self.repo.listar(nota_min)

7.3.4 Router (capa de presentación)

# routers/alumnos.py
from fastapi import APIRouter, Depends, HTTPException
from services.alumnos import AlumnoService
from repositories.alumnos import AlumnoRepository
from models.alumnos import AlumnoCreate, AlumnoResponse

router = APIRouter(prefix="/alumnos", tags=["Alumnos"])

async def get_alumno_service(conn = Depends(get_db)):
    repo = AlumnoRepository(conn)
    return AlumnoService(repo)

@router.post("/", response_model=AlumnoResponse, status_code=201)
async def crear(
    datos: AlumnoCreate,
    servicio: AlumnoService = Depends(get_alumno_service)
):
    try:
        return await servicio.inscribir(datos.nombre, datos.nota)
    except ValueError as e:
        raise HTTPException(status_code=400, detail=str(e))

@router.get("/", response_model=list[AlumnoResponse])
async def listar(
    nota_min: float = 6,
    servicio: AlumnoService = Depends(get_alumno_service)
):
    return await servicio.listar_aprobados(nota_min)

@router.get("/{id}", response_model=AlumnoResponse)
async def obtener(
    id: int,
    servicio: AlumnoService = Depends(get_alumno_service)
):
    try:
        return await servicio.obtener(id)
    except ValueError as e:
        raise HTTPException(status_code=404, detail=str(e))

🔐 8. Transacciones — Todo o nada

8.1 El problema de las operaciones parciales

Imaginá una transferencia bancaria: restás $100 de la cuenta A, pero justo antes de sumarlos a la cuenta B, el servidor se cae. Resultado: el dinero desapareció.

Una transacción garantiza atomicidad: si cualquier paso falla, todo se deshace automáticamente. Es el principio ACID de las bases de datos relacionales.

8.2 Sintaxis en asyncpg

async with conn.transaction():
    # Todo lo que pase acá adentro es UNA sola transacción
    await conn.execute("UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1")
    await conn.execute("UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2")
# Si algo lanza excepción → ROLLBACK automático
# Si todo sale bien          → COMMIT automático

8.3 Ejemplo completo: Transferencia con validación

class TransferenciaService:
    def __init__(self, repo: CuentaRepository):
        self.repo = repo

    async def transferir(self, origen_id: int, destino_id: int, monto: float):
        if monto <= 0:
            raise ValueError("El monto debe ser positivo")
        if origen_id == destino_id:
            raise ValueError("Origen y destino no pueden ser iguales")

        async with self.repo.conn.transaction():
            origen = await self.repo.obtener_por_id(origen_id)
            if not origen:
                raise ValueError("Cuenta origen no existe")
            if origen['saldo'] < monto:
                raise ValueError("Saldo insuficiente")

            destino = await self.repo.obtener_por_id(destino_id)
            if not destino:
                raise ValueError("Cuenta destino no existe")

            # Las dos operaciones juntas, si falla una → ROLLBACK
            await self.repo.actualizar_saldo(origen_id, -monto)
            await self.repo.actualizar_saldo(destino_id, monto)

            return {"mensaje": f"Transferidos ${monto} exitosamente"}

8.4 Transacciones anidadas (savepoints)

Podés crear "puntos de guardado" dentro de una transacción grande:

async with conn.transaction():
    await conn.execute("INSERT INTO logs(accion) VALUES('inicio')")
    
    try:
        async with conn.transaction():  # savepoint anidado
            await conn.execute("UPDATE productos SET stock = stock - 1 WHERE id = 5")
            raise Exception("Algo falló!")
    except Exception:
        # Solo se revierte el UPDATE del producto, el log sobrevive
        pass
    
    await conn.execute("INSERT INTO logs(accion) VALUES('fin')")

8.5 Niveles de aislamiento

asyncpg permite especificar el nivel de aislamiento de la transacción:

async with conn.transaction(isolation='serializable'):
    ...  # Máxima seguridad, menor concurrencia

async with conn.transaction(isolation='read_committed'):
    ...  # Por defecto, buen balance

📋 9. Resumen y ejercicios

Lo que aprendiste hoy

  • Lifespan: startup (crear pool, cargar config) y shutdown (cerrar conexiones) de tu app.
  • Depends: inyección de dependencias. Tus rutas piden lo que necesitan y FastAPI se los provee.
  • asyncpg: el driver más rápido para PostgreSQL en Python. Protocolo binario, async nativo.
  • Pool: recicla conexiones para no saturar PostgreSQL. Siempre usar acquire() con with.
  • 3 capas: rutas (HTTP), servicios (negocio), repositorios (SQL). Cada capa tiene una sola responsabilidad.
  • Transacciones: atomicidad garantizada. Si algo falla, todo se revierte.
  • Placeholders $1, $2: previenen SQL Injection. Nunca concatenar strings en queries.

🧪 Ejercicios para practicar

  1. CRUD completo: Creá un endpoint /productos con stock. Implementá todas las operaciones con sus 3 capas.
  2. Compra con transacción: Al comprar, restar stock y registrar la venta en otra tabla. Si falla el registro, que el stock no se reste (transacción).
  3. Filtros avanzados: Agregá query parameters para filtrar por precio mínimo/máximo, ordenar por nombre/precio. Usá Depends para parsear esos filtros.
  4. Autenticación: Creá un Depends que lea un header X-API-Key y valide contra una tabla de api_keys.
  5. Rate limiting: Usá app.state para guardar un contador de requests por IP y bloqueá después de 100/min.
  6. Testeo: Escribí tests con pytest-asyncio y una BD de prueba. Mockeá el pool para no depender de PostgreSQL real.
  7. Migración de librería: Convertí un endpoint que use psycopg2 a asyncpg. ¿Qué cambió? ¿Qué ganaste?
